# 按模块横切、按业务纵切推进

[根 TODO](../../TODO.md)是每日查看入口，[tasks.json](tasks.json)是唯一可编辑状态源。横向模块 H01—H10 表示能力归属；纵向批次 V00—V22 表示可完整验收的业务交付。批次大小不等，完成批次数不能当作整体项目完成百分比。

## 状态维护

1. 开始一批前，在任务源标记 `in_progress`，明确模块、依赖、范围、验收条件及预期验证命令。
2. 实现代码并执行必要测试；在新台账中记录真实结果，同步 README 与相关 Wiki。
3. 全部验收通过后，将该批 `checks` 标为 passed，填写 evidence 文件、ledgers 与 completed_on，清除 blocker，再标记 done。
4. 运行 `npm run todo:sync` 生成复选框，运行 `npm run check:todo` 和 `npm run check:changes`。完成一批即更新一批，不等全部项目完成再更新。
5. 未执行、部分通过或仍缺必需外部验收时不得打勾。需要真实模型/商户/邮件/存储配置的批次写清条件，不能只因fixture成功就判真实接入完成。

```sh
npm run todo:sync
npm run check:todo
npm run test:todo
```

不要直接编辑生成的 TODO.md；检查会拒绝任务源与展示不一致。任务源中的证据必须是仓库内已存在文件；不得放密钥、密码、会话或真实个人数据。检查能验证依赖无环、编号唯一、完成条件字段和证据存在，不能自动证明命令真的执行过，仍需审阅台账与测试输出。

## 拆分原则

- 横向模块不能以“有一个文件/一个页面”作为完成标准；它可能贯穿多个批次。
- 纵向批次至少覆盖输入、权限、持久状态、执行/交付、前端反馈、恢复/错误和适用验证，不将空壳入口标完成。
- 并行任务按文件归属分工，共享状态机、路由和迁移由明确的集成人维护。
- 发现范围扩大时拆出新批次并保留依赖和旧证据；不要改写已交付台账或删除未完成任务来提高完成率。
- 每轮结束明确本轮完成、尚在推进、待外部条件和全产品放行差距。
