# 权益账本与任务结算

关联批次V12；实现记录见[043台账](../changes/2026-11-13-043-credit-ledger.md)。入口、价格文件和离线操作见[权益配置与离线核账](billing-operations.md)，供应商计量语义见[聊天用量证据](chat-usage.md)，设计取舍见[ADR 0009](decisions/0009-credit-ledger.md)。

## 启用与单位

`BILLING_MODE=disabled`是默认值，新生成保持原行为。`credits`必须同时配置PostgreSQL、`AUTH_MODE=required`和明确的价格目录；不能在内存演示模式中模拟持久余额。无自动赠送、注册充值或公开增款接口。

单位固定`CREDIT`，精度6，1 CREDIT等于1,000,000 micros。这是平台权益额度，不是人民币、供应商成本或已接入的支付余额。Go/PG使用有符号64位整数，公开金额使用十进制字符串；单笔、账户投影和累计金额均有9,000,000,000,000,000 micros的策略上限。计算使用整数乘法与一次向上取整：`ceil((input_tokens × input_rate + output_tokens × output_rate) / 1,000,000)`，不经过JavaScript浮点或字符数计价。

当前仍为控制连接单写者。账本事务锁定工作区钱包，涉及系统发行/收入账户的分录也串行锁定；此实现优先保证余额一致性，不能宣称已达到总体方案的分布式账务或极限吞吐目标。

## 报价、原请求与受理

报价绑定工作区、项目、资源类型、会话（如有）、完整原始输入的规范JSON散列、模型版本、价格版本、供应模式及明确预算/媒体规格。报价表不保存提示词或输出正文。任务参数在执行时规范化，但报价散列来自规范化前的客户端输入；`quote_id`从报价绑定散列中去除，仍包含在平台请求幂等散列中。

有效期10分钟。每工作区最多64个尚未消费的有效报价，全库最多10,000个；插入前可清理最多1,000个已过期超过一天且从未消费的报价。已消费报价保留。报价是有效期内的价格承诺，服务重新加载新价格不改写已发报价；新请求仍须通过当前模型目录和权限校验。

生成原幂等键先查已受理结果，再检查报价、模型启停、CAS、余额和容量。相同键相同输入返回原资源，不再次冻结；相同键不同输入返回409。未知受理保留原body/key/quote，不能因为报价过期或余额变化换键自动重新提交。

受理在工作区钱包锁内同时预留累计结算空间：`累计已结算 + 所有剩余冻结（含REVIEW） + 新冻结 ≤ 整数策略上限`。使用冻结账户的同事务投影读取剩余hold，采用减法避免溢出；超限返回409 `LEDGER_CAPACITY`，报价未消费、资源未创建、没有供应商调用。全额冲正恢复可用额度，但不会清零历史累计结算；因此余额充足不等于仍有累计结算容量。原幂等重放仍优先，不受此新受理检查影响。这样已受理的冻结都有足够的终态结算空间，避免完成作品后才发现累计上限。

`Run`、`Task`、报价单次消费、reservation、冻结分录、原幂等记录、审计和Outbox在同一PG事务内提交。只有确认提交成功才入执行队列或替换缓存。数据库提交ACK丢失时服务fail closed，不把未确认的内存Billing暴露成成功；重启从数据库恢复原资源和原冻结。

## 分录和投影

012新增钱包、账户、报价、reservation、journal、posting及离线操作幂等表。每个journal至少两个posting且总和为零，数据库延迟约束在commit时检查；journal、posting及离线操作记录拒绝UPDATE/DELETE。

| 动作 | 负向分录 | 正向分录 |
| --- | --- | --- |
| 离线授予 | 系统发行 | 用户可用 |
| 受理冻结 | 用户可用 | 用户冻结 |
| 消费结算 | 用户冻结 | 系统收入 |
| 未消费释放 | 用户冻结 | 用户可用 |
| 全额冲正 | 系统收入 | 用户冻结 |
| 冲正释放 | 用户冻结 | 用户可用 |

账户余额及钱包累计结算/冲正是事务内维护的投影，不能替代不可变原始分录。退款是原CHARGE journal的一次完整反向分录，`reversal_of`唯一；再用独立分录释放给可用额度。不会修改原消费，也不会撤销早先已释放且可能被用户花掉的剩余冻结额度。

公开流水是journal的安全投影，展示`CREDIT/RESERVE/CHARGE/RELEASE/REFUND/REFUND_RELEASE`、金额及可用/冻结变动。私有系统账户、供应商凭据、提示词、输出和离线证据正文不进入公共流水。

## 运行状态和结算状态分别维护

`Billing`包含报价/冻结ID、价格版本、状态、原冻结/已结算/已释放/已冲正金额、单位、精度和版本。`HELD`或`REVIEW`的剩余冻结为`reserved - charged - released`；钱包`review_micros`是总冻结中的待核实子集，不另加进余额。已结算累计和已冲正累计分别保留，净消费可由两者相减理解。

| 情况 | 处理 |
| --- | --- |
| QUEUED在开始前取消，或进程重启中断且未曾持久化开始标记 | 释放原冻结 |
| LLM正常COMPLETED、完整DONE、合法一致usage、来源与冻结供应模式匹配、输入/输出不超冻结预算 | 按实际报告token结算，释放余款 |
| LLM取消、失败、中断、缺usage、非法或不完整usage、超预算、demo与gateway证据错配 | REVIEW，保持剩余冻结 |
| 媒体SUCCEEDED/PARTIAL且已经在同事务注册1至原请求数量的产物 | 按冻结的平台单件SKU乘实际交付数结算，释放余款 |
| 媒体开始后失败、无产物、SUBMIT_UNKNOWN、RECONCILE_REQUIRED或临时PROVIDER_STATE_UNKNOWN | REVIEW，保持剩余冻结 |

LLM在网络调用前先持久化RUNNING与开始标记；媒体在POST前先持久化SUBMITTING与开始标记。进程宕机或网络错误不能凭“没有输出/没有handle”认定供应商未收费。媒体的网关`quota/cost`没有明确单位，不用于构造用户账单。生成完成与结算完成是两个独立事实。

Run每token仍只走内存SSE；既有有界检查点和终态事务才访问PG。取消后迟到的usage不会复活运行、重开冻结或自动收费。当前不在后台重新抓取丢失usage；人工核实需提供可信计量及不含秘密的证据标识。

## 恢复、租约和故障

同一Task状态写入先执行owner/epoch/generation/版本/租约期限条件更新，成功后才登记产物及账务；它们仍在一个事务里。旧worker的迟到结果不能单独记账。Outbox满导致状态、产物和分录整体回滚，保留原执行结果后只重试保存事务，不重新POST/Stream。候选对象只在commit成功后替换缓存。

恢复的已开始LLM被标记INTERRUPTED并转REVIEW；从未执行的排队LLM中断可释放。已有媒体handle继续查询，未知提交保持待核实；媒体成功交付后仍依据原报价结算。切换当前价格或关闭新请求计费，不重写已有reservation；旧资源没有reservation则完全不追扣。

离线`resolve`只处理REVIEW且业务已终态或停在SUBMIT_UNKNOWN/RECONCILE_REQUIRED的资源。仍在自动执行/查询的PROVIDER_STATE_UNKNOWN返回`LEDGER_EXECUTION_ACTIVE`，不能提前释放后让调度器继续完成。人工release必须附原因和证据标识；人工charge只能使用冻结规则内的真实计量或交付数量，不能任填扣款金额、超剩余hold。

人工核实是明确终结该冻结的决策。若已人工释放的parked媒体后来被用户“重新核对”并成功取得作品，系统不会自动再次收费或另开冻结。操作人员必须先完成外部核对再作释放决定；这是当前人工控制面的明确边界。

离线冲正/核实同步增加关联Run序号或Task版本并写Outbox；前端重连补读可发现新的Billing。账户增款没有伪造生成资源事件，余额通过只读接口重新获取。

## V14-A 线上人工核实

[运营异常工单](operations-cases.md)提供默认关闭的线上入口：finance可对REVIEW执行`release`或`charge`，operator可对已知handle的停驻媒体执行`reconcile`，仅查询原请求。权限按指定工作区实时重核；执行须先预演并确认当前密码，计划消费、工单回执、运营审计及适用的账本、业务状态和Outbox同事务提交。线上charge/release复用上述冻结规则，不能任填扣款额；预演不保留业务分录，受理不明只读回执核对。

赠额及已结算权益的完整冲正仍使用[离线管理工具](billing-operations.md)，本次没有开放线上赠额或退款。`release`是解冻未结算的创作点，离线`refund`是内部CREDIT冲正；两者都不是支付渠道的真实货币退款。`no_action`仅关闭运营工单，不改变任务或余额。完整V14的内容审核、封禁、申诉与风控仍未完成。

## 核账与升级

只读核账分别检查journal借贷平衡、posting汇总与账户投影、钱包两个用户账户是否存在、冻结余额与reservation剩余、累计结算/冲正与原journal及reservation。发现差异仅报告，不自动补分录或覆盖余额。操作幂等记录持久保存请求散列与结果，重复键只重放，变更内容拒绝。

012只增加新账本，不为历史Run/Task补扣或生成虚假充值。应用和离线CLI继续遵守单写者及精确迁移版本栅栏。升级前联备PG、私有资产/参考目录及邮件队列密钥；不能删012登记再运行旧程序。回退需停止服务并将升级前联备恢复到独立数据库/目录，核对owner身份后整体恢复。

本模块PG专项覆盖整数运算、并发余额、幂等增款、真实commit ACK丢失、结算/冲正、缺失usage、部分交付、恢复、事务回滚、Outbox背压及旧lease拒绝。HTTP/UI、真实进程Kill、离线CLI与最终全量结果由联合台账分别记录。测试fixture不等于真实供应商账单或支付渠道验收；本批没有真实付费调用。
