# 媒体原任务查询的容量基准

## 规划指标

原方案按 100 个新媒体任务/秒、受理至终态平均 600 秒，估算 60,000 个在途任务。每 10 秒查询一次需要 6,000 次查询/秒；单次平均耗时 200 毫秒，需要约 1,200 个并发查询。若供应商只允许 2,000 次/秒，60,000 项的平均间隔至少 30 秒。调度指标单独统计实际发起查询相对计划时间的迟滞，正常负载目标为 P95 ≤ 500 毫秒、P99 ≤ 2 秒。任务状态提交至前端消费另有 P95 ≤ 300 毫秒、P99 ≤ 1 秒的目标。[设计方案](../deliverables/Go与NewAPI高性能AI工作台开发方案.html)

## 可复现实验

使用 `internal/studio/media_query_capacity_test.go`。实验分别配置 2 和 16 个查询 worker，工作区和渠道预算均为 16，空闲扫描间隔为 20 毫秒。每档预置同一项目、同一渠道的 128 个已受理 handle，首个到期时间预先固定，后续每 25 毫秒到期一个。所有计划时间在开始前确定，较慢的一档会积累排队时间。生产预选与执行照常运行，测试不按任务 ID 手工领取。每个原 handle 只接受一次本机 HTTP GET，夹具在 200 毫秒后返回固定终态，以便逐项检测漏查、重复查询及意外提交。

- `ScheduleToDispatch` 从原始到期时间算到生产 HTTP 客户端进入 RoundTripper。`ScheduleToWire` 算到 `httptrace.WroteRequest` 成功回调，包含获取连接及发送请求的耗时。另对照 `ScheduleToHandler`、`HandlerService`、`WireToHeaders`。
- 毫秒分布给出均值和最近秩 P50/P95/P99/最大值。吞吐以首个到期时间至确认整组终态的窗口计算，包含最后一个请求的排空时间以及最多一次 10 毫秒采样间隔。MEMORY 读实际任务状态；PG 读取任务 JSON、原 handle、租约释放与非活跃投影。
- 检查每个原 handle 的真实 GET、成功写出、HTTP 到达及响应各一次，实际成功领取 128 次，并验证零意外路径、零提交步骤和零 POST。输出仅包含聚合数据。

在仓库根目录运行内存档。PG 档按仓库单写者规则由集成人串行运行，`TEST_DATABASE_URL` 使用既有隔离测试配置，每档使用新 schema。

```powershell

go test -v -count=1 -timeout=150s ./internal/studio -run '^TestMediaOriginalQueryCapacity$'
go test -v -count=1 -timeout=150s ./internal/studio -run '^TestPostgresMediaOriginalQueryCapacity$'
```

## 原 handle 查询连接共享

`MEDIA_QUERY_DB_CONNECTIONS` 默认为 0。PostgreSQL 模式可显式设置为 1 至当前 `MEDIA_QUERY_WORKERS`，最高 32，重启生效。查询 SQL 池独立于提交、交付、审核及控制写者的连接。查询 worker 在 HTTP 期间仍占用工作区和渠道预算。达到最近一次确认的租约期限时会取消在途 GET。已知响应遇到任务行争用可只重试保存。

在相同的 40 次/秒投放和 200 毫秒响应下，242 的容量档提供 32 个 GET 执行位与 4 条租约连接，沿用 241 的工作区及渠道上限 16。慢连接专项另使用工作区及渠道上限 32，在至少 8 个实际 GET 同时等待时借出全部 4 条查询连接。由集成人配置隔离 PG 后串行执行。

```powershell
$env:STUDIO_MEDIA_QUERY_MEASURE = '1'
go test -v -count=1 -timeout=180s ./internal/studio -run '^TestPostgresPooled'
```

在同一 PostgreSQL 16.14 配置下，32 个查询执行位共享 4 条租约连接，单工作区和渠道上限均保持 16。按每秒 40 个到期、上游平均 200 毫秒投放，128 次全部完成且无 POST。实际峰值为 11 个并发，完成率 37.81 次/秒，到期至写出 P95 为 39.53 毫秒、P99 为 73.87 毫秒。慢查询独立用例核验 GET 阻塞期间四条数据库连接均可立即借出。[完整指标](assets/media-pooled-query-capacity-039.json)

## 040 扩展查询并发

`MEDIA_QUERY_WORKSPACE_CONCURRENCY`、`MEDIA_QUERY_CHANNEL_CONCURRENCY` 默认为 0，分别继承普通工作区和渠道配置。可独立设置 1—1,536，实际生效值最高为查询执行位数。新启动的大档服务由一个派发者按原公平游标选择任务，旧渠道的冷却时间、探测身份及已降级的并发额度随所在行继续生效。Prometheus 的 `studio_media_query_dispatch_attempts_total` 按进程累计派发尝试，包含空队列和遇到背压的次数。

本机 PostgreSQL 专项以 1,536 个配置执行位、4 个数据库连接、单渠道上限 256 接受 260 个既有原 handle，核对 256 条真实 GET 同时等待时的占位、其余请求的背压，以及完成后的逐任务终态。用以下命令在隔离 PG 串行验证。[040 决策](decisions/0040-original-query-capacity.md)


### 32、64、128 个执行位的到期曲线

使用同机 PostgreSQL、同一个冻结渠道和同一回环 HTTP 服务，每档独立预置 512 个原 handle，每秒安排 320 个到期，服务每项等待 200 毫秒。三档都申请四条查询数据库连接，工作区和渠道的配置均为 128。32 档使用原查询工作线程，较高两档使用单派发者。应用与 PG 配置、实际服务耗时及有效作用域上限随每档聚合输出。

待写积压等于已经到期且尚未写出 GET 的任务数，按每项的到期时间与 HTTP `WroteRequest` 重建。完成率只计独立 SQL 已确认终态、已释放租约及非活跃投影的任务。实际 HTTP 峰值取服务端接收计数，执行位和作用域峰值每 10 毫秒采样。到期前用生产 SQL 核验页行数，执行期间以实际候选检查数衡量扫描成本。该项只允许回环地址或本机 Unix 套接字的 PG 配置。

```powershell
$env:STUDIO_MEDIA_QUERY_CURVE = '1'
go test -v -count=1 -timeout=5m ./internal/studio -run '^TestPostgresOriginalQueryRateCurve040$'
```

### 按阶段定位查询耗时

248 使用同一份 040 测量和同样的 4 条租约 SQL 连接。以每秒 320 个到期分别采集 32、64、128 个执行位的结果。额外的慢 GET 用例持续等待到真实心跳续租返回，用于核对心跳计时。每档的 `MEDIA_QUERY_STAGE_TIMING_248` 聚合覆盖公平选择、严格领取、交接、首次续租及心跳、到期到写出、HTTP、已知响应的应用锁等待、控制写互斥等待及保存事务。

每个阶段报告样本数、累计毫秒及 P50/P95/P99。`WindowOccupancyMS` 是该阶段各样本与测量窗口交集的总时长，除以 `WallMS` 得到平均并发。`ActiveWallMS` 是所有交集的并集时长。总续租内含查询连接等待和事务，总保存内含控制互斥等待与保存事务，网关服务时间与 HTTP 等待也会重叠。性能比较保留各自测量窗口。[248 台账](../changes/2026-11-23-248-query-stage-timing.md)
