# 040 · 单控制写者下的原任务查询容量

## 决策

33—1,536 个显式查询执行位由一个派发者调用原工作区和任务分页选择器。每次先占执行位，再申请工作区与原渠道预算，严格领取进库后才允许交接。空队列按配置的轮询间隔休眠，已领取查询完成会唤醒派发者，通知最多缓存一个。每个发起的执行独立归还预算。预选和心跳共用 242 的固定查询连接池。

## 原因与可选方案

242 已将 HTTP 与数据库连接分离，但 020 的查询并发和渠道约束上限为 32。为每个额外执行位常驻一个数据库轮询者，会使空队列读取量随配置数增长。通过新的渠道分桶来取得更多额度，会使同一凭据的冷却和探测失去约束。040 仅调整原行的检查约束并复用既有权责。

## 影响与状态

配置大档时，交接后的首次外发除核对冻结身份及实到期租约，还在取得原任务投影与原渠道行锁后核验到期、冷却、探测、动态降额。后续心跳和落库继续受代次、所有者、业务版本及原 handle 约束。已有渠道需要按既有成功恢复规则逐步升额。每批仍受单个公平选择器、查询 SQL 连接和控制写者提交速度约束。运行设置及验证命令见[查询基准](../media-original-query-capacity.md)，实测状态见[244 台账](../../changes/2026-11-23-244-large-original-query.md)。

派发时按数据库中的原领取和当前渠道核验，再把原 GET 交给 HTTP Transport。连接排队期间本地检查已确认的租约到期时间，取消或渠道状态变化与网络写入并非同一事务。已派发的 GET 可能到达上游；此后仍须持有有效代次与版本才能保存结果。
