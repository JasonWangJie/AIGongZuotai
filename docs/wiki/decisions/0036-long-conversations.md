# 036　持久化长会话与有界上下文

## 决策

PostgreSQL 启动时建立 036 格式。只有显式设置 `LONG_CONVERSATION_HISTORY_ENABLED=true` 才接受超出原 128 个分支节点或 256 个会话节点的新一轮。新硬上限分别为 16,384 和 32,768，内存演示保留原有额度。恢复默认配置后，已有长分支可按原项目和原叶读取。已受理请求的原键、冻结价格和上下文仍要核对原收据。

## 选择依据

按整条历史构造消息页和模型上下文，大输出或大量不可公开的旧轮会使一次翻页或输入反复读回不相关的正文。只保存之前某次模型调用选择的上下文，也无法在更换模型窗口或创建不同分支时还原当前业务语义。036 为不可变消息建立深度、祖先跳点和更早的可用完整轮次索引。服务仍以当前获准公开的原 Run 和用户消息校验选中的正文，然后按完整轮次、模型窗口和输出保留量裁剪。缺少证据时拒绝构造新的执行请求。

## 数据与恢复

迁移按旧树拓扑回填，不重写原消息、冻结执行、账务、身份或原幂等记录。分支深度按选中叶计算。客户端的分页游标能被读出，服务端在账户、工作区、项目、会话和指定叶的作用域内验证成员关系。历史缓存可淘汰正文，分页和重读都只发出授权 GET。

升级前停写并联备 PostgreSQL、私有目录和原 owner、启用的交付及队列密钥、已登记对象版本。回到旧制品需同步恢复对应的旧格式备份。只需收紧新写入时使用 036 配置开关。离线资产维护、迁移、权益和运营管理、只读财务核对继续匹配完整迁移登记。

## 单分支 10,000 条持久消息

本机 PostgreSQL 通过正常受理入口完成同一分支 5,000 轮，逐轮核对上游上下文。Chromium 读取 500 个授权页、索引 10,000 条消息，实测最多挂载 10 行、缓存 120 条正文；首、中、末三处淘汰内容均通过原页重读。显式继续后原库有 10,002 个节点与 5,001 份冻结上下文，原键重放未增加上游调用。专项 219.573 秒。 这组短文本下正文缓存采样峰值 2,040 字节；8 MiB 字节边界另由多字节大正文专项验证。数据库业务表及索引由 3,891,200 增至 103,063,552 字节，含该轮会话产生的运行及冻结等记录。 [聚合数据](../assets/performance-conversation-history-036.json)。
