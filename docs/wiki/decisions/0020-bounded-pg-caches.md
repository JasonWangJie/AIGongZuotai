# 0020 · PG 缓存保留、执行退出与项目范围

## 背景

高积压工作区曾因全局缓存条数使其他工作区收到 503。090 解除了媒体受理限制。恢复缓存、普通与会话聊天、媒体 worker 和 SSE 仍需共享同一套资源生命周期。数据库持有控制写锁，项目和媒体资源均可按键查询。

## 决策

- 启动按既定分页顺序处理所有待恢复记录。每类只保留最多 `MaxRecords` 个闲置 Run 或媒体任务。项目由数据库按工作区查询；默认项目按创建时间和 ID 稳定选择，项目数量上限和审计在工作区锁保护的创建事务中执行。
- PG 原键、权限、权益及真实准入决定能否受理。运行期间，正在排队或由 worker 执行的 Run，以及仍有 SSE handler 的 Run 可以临时超过闲置预算。慢消费者离开发送集合后，handler 自己的占位仍保留到退出。已领取但遇到关闭的非终态 Run 留到停机保存。保存遇到确认回滚的背压，实际消费旧事件后才重试。
- 媒体领取在已获 lane 许可的执行段内按任务统计尚未退出的尝试。取消、运营核实与换租约可以先撤销数据库写权限。占位在实际 I/O、审核、心跳与保存退出后释放。迟到尝试按租约身份清理，提交成功的资源版本才允许替换缓存。
- 现有冷读在应用互斥锁内完成 PG 读取与选择性填充；排队、运行及读者不使用缓存淘汰释放额度。运营处置提交后，热 Run 的同一版本写入 SSE 快照以供旧游标补读。

## 考虑过的方案

提高进程缓存上限会把误拒推迟到更大的积压。按终态统一淘汰会丢失仍未退出的执行或订阅。锁外冷读需要协调并发填充与版本冲突，本次保留原来的序列化读取方式。

## 实施与代价

已接入两种聊天入口、媒体四个通道、Run SSE、项目授权和完整启动。空槽不足时，冷门资源的重复访问会产生 PG 查询。保留条数与业务载荷的 JSON 编码字节分别测量，后者不含 Go 堆、连接驱动或操作系统缓存。系统继续使用单控制写者。实测见[094 联合台账](../../changes/2026-11-21-094-bounded-startup.md)。
