# ADR0014 · 单写者聊天公平执行

日期：2026-11-14。状态：A1实现完成，联合验收见[067](../../changes/2026-11-14-067-execution-integration.md)；V16完整范围见[契约](../../planning/v16-contract.md)。

## 原因

原聊天FIFO仅限制全局worker与总缓冲，深队列工作区可使后入其他用户等待同一长队；受理总量限制不能替代正在执行数量。公开模型别名还可能映射同一私有上游模型，按公开ID限执行会漏掉共享供应预算。

## 决定

当前控制写者内按workspace轮转，并同时执行全局、workspace和受理冻结upstreamModel预算。总等待队列和单workspace队列独立有界。一个workspace的模型已满时，可选择其后续其他模型，保留同workspace/model顺序。HTTP池不超过worker预算。

同一业务锁内检查容量并持有至受理事务提交确认，之后无阻塞入队。运行到provider、输出审核及终态保存全部退出才释放执行名额；取消排队项则在取消事务成功后立即移除。原幂等检查继续优先，不为调度引入第二个持久受理状态。

## 替代项

- 保留全局FIFO并增大worker：增加连接占用但不解决工作区队首阻塞。
- 每个任务启动goroutine再等待信号量：容易堆积无界等待，且取消/事务确认边界更难审查。
- 立即引入分布式队列：缺少持久流fencing、共享控制写者和私有存储并发验收，不能只换队列即宣布多实例成立。

## 后果与实施边界

公平按可执行机会计，不抢占长流，不保证同耗时公平；配置默认workspace同时执行2，会让同一workspace四并发测试的一部分首字等待包含排队时间。性能报告必须列出配置与队列等待口径，不能和旧4活跃流直接比较。
