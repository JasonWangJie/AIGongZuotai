# ADR0015：媒体提交与查询交付分别预留资源

状态：2026-11-14实现，V16-A2本地已验收；最终验收见[071](../../changes/2026-11-14-071-media-lane-integration.md)。

## 原因与选择

共享媒体worker与HTTP池时，慢提交可占满查询原handle的机会；只调整HTTP连接数不能解决已经被占用的worker和PG辅助连接。按不可变handle是否存在划分submit和query，分别配置1—32个worker，默认2+2；先取得本通道预算及连接再领取持久租约，没有容量则返回下一轮。查询步骤目前包含下载、导入、审核和提交，不宣称这四阶段已独立。

JSON提交与multipart编辑共享submit Transport，GET查询使用query Transport；下载继续走独立且受SSRF约束的客户端。内存模式直接扫描有界任务缓存，使用attempt身份和预期业务版本阻止迟到覆盖，不增加第二个待执行队列。PG模式仍依赖单控制写连接和owner/epoch/generation/版本栅栏。

## 替代项

- 只增共享worker：可缓解平均延迟，无法保证提交与查询互不耗尽对方资源。
- 领取后再排队等待本地信号量：持有租约却无法开始，可能过期重领或放大数据库领取压力。
- 本批立即拆分导入与审核：需要冻结结果描述、持久阶段移交、恢复与候选唯一性设计，不能直接让新worker重审B2旧候选；保留为A3的独立完整链路。

## 后果与限制

运行取消不提前释放预算；实际I/O、审核及终态保存退出后释放。没有handle的SUBMITTING过期保持待核实，不因新lane重POST。已有候选不自动重审，整组交付与账务仍以确认事务为准。新环境配置启动生效；旧Go TaskWorkers=1兼容为最小1+1，不能说仍总并发1。

本批不改变017格式或SQL字节。领取沿用已有混合next_poll索引，在单lane大积压下可能扫描另一lane记录；目前保证执行资源隔离，未证明领取查询成本隔离。A3需实测EXPLAIN、积压和候选阶段，必要时通过新迁移改善索引。固定指标仅两lane，不暴露任务/租户/凭据；本机fixture不等于生产容量。

[执行通道](../media-execution-lanes.md)、[HTTP通道](../media-transport-lanes.md)、[验收契约](../../planning/v16a2-contract.md)。完整V16仍包括A3导入/渠道、B持久流及C综合测量，未将拆出子批当成缩减需求。
