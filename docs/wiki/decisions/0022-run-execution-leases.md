# 0022 · 聊天执行租约与已提交回答的恢复

## 背景

021 记录每个 Run 的单次执行身份和已提交增量。数据库还需要判断正在写入的进程是否仍有执行权。例如，输出审核可以在用户取消或重启之后才返回 ALLOWED。

## 决策

022 为新 Run 的流头登记租约。在已取得控制写锁的启动事务中更新聊天执行代次，进程保留它在启动时取得的代次。领取与 RUNNING 转换同事务，提交确认后才可首次请求模型。后续写入核验执行身份、持有者、领取轮次、进程代次和数据库时钟上的有效期，增量与检查点还需匹配已提交序号。续租等待数据库行锁时也可能失权。

可信的取消和恢复路径在数据库锁内读取已提交的公开前缀，再保存相应的终态。没有获得输出审核批准的候选继续留在原执行的有界私有内存里。旧执行即使稍后得到批准，也不能据此写入正文、扣除权益或广播事件。进程中的真实模型、审核与保存调用退出后才释放本地执行槽。

## 替代方案与后果

仅靠进程时钟或请求上下文取消，无法约束迟到的数据库事务。让旧执行重新读取当前代次会把新写者的权限交给旧调用。允许到期后重新领取已启动 Run 则可能产生第二次模型请求。数据库租约增加定期续约的事务成本；失权后可保留已提交的回答前缀，继续生成由用户显式发起新请求。

## 实施范围

已有 021 Run 保留原执行身份、正文和游标，升级时不授予新租约。020 及更早的 Run 继续使用其原快照恢复规则。离线工具要求完整 001—022，升级前联备 PostgreSQL、私有目录、目录归属、已启用的密钥和相关对象版本。控制写锁和目录锁继续生效。验收记录见 [103](../../changes/2026-11-21-103-run-lease-integration.md)。
