# 单控制写者下的受管聊天执行进程

## 背景

原执行器在控制进程内最多同时运行 64 个聊天。本机通过普通 API、模型 HTTP 流、持久日志与授权 SSE 验证了 64 个活动运行。独立批量日志实验另行测量了万条逻辑流。扩大正常聊天的同时执行数，仍须保证每个已受理 Run 只能使用其冻结请求与原执行租约。

## 决策

保留一个持有数据库控制锁和私有目录锁的服务进程。它可以启动同一可执行文件的多个聊天执行子进程。受管进程通过继承的匿名管道握手，使用服务端传入的网关配置，只负责处理分给它的一次模型请求。控制进程负责会话受理、持久租约、逐段确认、用户 SSE、审核、权益和终态。数据库格式沿用 037。

工作区和冻结上游模型预算在控制进程统一扣减。受管槽只供具有持久冻结上下文的新会话使用。直接创建的 Run 使用原本地槽。申请新工作前先取得已就绪槽，再以同一运行、执行身份、租约代次和 owner 派发。输出逐段确认，额度或审核开启时，控制进程继续按原规则决定可见内容和入账时点。

## 配置和回退

同时设置 `CHAT_CHILD_PROCESSES`（1–16）及 `CHAT_CHILD_SLOTS`（每个进程 1–64）可启用受管模式。它要求 PostgreSQL、必需鉴权和已配置的 live 聊天网关。两项都省略时使用现有本地执行器。`CHAT_WORKERS` 继续控制本地执行位；工作区、上游模型和等待容量使用原设置。启用前应按两类执行的总占用配置相应资源。

子进程失联时，已领取的执行保留已确认前缀并进入中断处理。子进程全部失联后，仍在父队列且从未领取的会话可在原本地预算内首次执行。控制服务重启继续执行原有中断恢复。回退时先停止新的派发并排空，或按原规则中断在途工作，确认受管进程退出后去掉两项配置，用同一兼容制品重启。

## 替代方案和影响

直接提高单进程工人数无法证明跨进程归属和故障隔离。另起完整服务会争用数据库控制写者和目录锁。独立执行进程沿用现有业务事务，也保留父进程的数据库、账务、用户订阅和恢复容量约束。跨主机派发、多个控制写者和生产容量须单独验收。

运营指标使用固定聚合项记录已握手槽、在途执行、派发和本地首次执行。私有网关配置、原始请求和进程身份不会出现在指标标签中。子进程子命令由控制器启动，无需为它配置公共端口。

## 037 已执行的本机专项

标准服务在本机启动两个受管子进程，Windows TCP 归属与 PostgreSQL 租约分别核实每个子进程同时持有 40 条模型连接。5 个工作区各 16 条，4 个冻结模型各 20 条。80 个正常授权读者共读到 960 个原序增量，80 笔运行完成结算；模型写出到普通 SSE 读完的 P50/P95/P99 为 33.91/64.86/976.40 毫秒。另一个读者暂停约 2.07 秒。 排队取消未请求模型，已开始取消和单子进程或控制器故障的已执行运行进入 REVIEW。两个子进程全失时，只将两个尚未领取的排队请求交给控制器的一个执行位。含故障场景的标准制品共发出 87 次模型请求；隔离的审核测试宿主另发 1 次，屏蔽决定留下的候选公开增量为 0。两部分合计零额外或重复模型 POST。4 路试跑包 26.646 秒，正式档包 29.582 秒。 [正式报告](../assets/performance-managed-chat-037.json)。

## 16 个受管进程的本机档位

258 将进程池上限扩到 16。单进程至多 64 个执行位，每个执行位继续使用固定管道消息上限和逐段确认。满额时可同时预留 1,024 个 IPC 位。单控制写者的工作区与冻结模型各维持 64 路执行上限，持久增量待存限制仍为 320 项、8 MiB，等待上限为 5 秒。进度超过保存预算时沿用原背压和中断处理。

`integrated-1024` 使用 16 个冻结模型、17 个普通注册工作区，所有会话仍走正常报价和受理。单一真实来源在第 11 名用户前等待完整注册窗口。每条连接需同时匹配原 TCP 对端的受管进程、原执行租约、工作区与冻结模型；测试单独验证全部租约的到期时间确实向后延长，正常与迟读 SSE、权益结算和故障处理继续按实测记录。[258 台账](../../changes/2026-11-24-258-managed-chat-1024.md)
