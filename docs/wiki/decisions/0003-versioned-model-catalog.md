# ADR 0003：版本化模型目录与执行快照

日期：2026-11-13。状态：V06实施，验收证据见[021台账](../../changes/2026-11-13-021-model-integration.md)。

## 问题

原先平台只有三个固定模型别名，参数按创作类型统一声明。增加模型后，图片尺寸、视频时长和分辨率并不一定能任意组合；配置变化还可能使已经排队的任务改用另一个上游模型。对用户显示新选项而没有服务端约束，会制造请求失败和重复生成风险。

## 决策

使用有大小和条数限制的服务端JSON目录，公开平台模型ID、说明、启停、版本和精确规格预设；上游模型映射仅服务端持有，URL与凭据继续来自环境。公开目录使用ETag重新验证，bootstrap与独立目录读取来自同一份启动快照。界面选择完整预设和数量，不以各字段的独立下拉推导出未经配置支持的组合。

新请求携带模型版本，服务端先查幂等，再检查新请求的启停、版本与参数；目录变化不会阻断原请求核对。受理时保存名称、版本、能力与实际参数；真实媒体同时准备并持久化原始上游提交体、摘要和原幂等键，提交前不再查新目录拼参数。已知handle继续用原供应商身份查询，不因模型停用丢失历史任务。

配置更改须重启进程生效。本阶段未实现管理端权限、热更新事务或跨实例传播，因此不提供未受保护的模型写入API。停止进程会按既有策略中断LLM，保存检查点；媒体重启恢复遵循原提交/查询状态机，不保证无感更新。

## 替代方案与取舍

- 直接转发网关模型列表：不能推导精确参数能力，且无法承担平台启停、历史版本和私有映射隔离。
- 任意参数透传：扩展快，但不能阻止无效组合或保证前后端一致。
- 本轮新增数据库管理端热更新：还依赖运营权限、配置审计和多实例分发，交由后续控制台及调度批次；本轮先验证执行快照正确性。

## 后果与边界

目录是操作者确认的能力声明，不是供应商实时健康或真实联调证明。兼容旧三个默认模型与旧幂等记录；pre-V06无原始提交体且无handle的live任务缺乏可验证执行身份，恢复时停在待核实，不能猜测新映射。历史名称优先使用受理快照，老记录无快照时显示原平台ID。

自定义模型及已移除模型占用继续被计入工作区限额；运维指标按固定kind与other桶汇总，不能将自由配置ID变成无限指标标签。该方案仍是单写者阶段，分布式配额、热更新、真实供应商验收有独立批次。
