# 工作区新生成准入

本页记录V14-C1受理门禁与独立moderator角色接线。工作区限制、申请复核、预演/密码确认和收据见[生成限制与复核](generation-controls.md)。C1不包含单次额度上限、账号整体封禁或内容人工放行，完整V14仍进行中。

## 覆盖范围

当前限制以工作区为单位，拦截新单轮Run、多轮回复/编辑分支/显式继续、图片/视频生成和图片编辑，以及新额度报价。用户不能通过切换同工作区项目绕过限制。默认没有限制记录时为OPEN。

限制只影响新的受理。已经接受的QUEUED/RUNNING任务继续原生成或原handle查询、审核和结算；原任务取消、已知handle核对、历史读取、已批准资产下载、账户安全、钱包查看和参考上传保持原权限与规则。解除新生成限制不放行B1/B2隔离内容，不重新发送供应商请求，也不改变既有额度冻结或结算。

`OPERATIONS_ENABLED=false`关闭运营管理入口，不能清除数据库已经生效的限制。PG账户服务重启后依然读取持久限制。默认memory演示不提供持久限制或运营权限；PG本地种子`ws_demo`仅在内部准入helper兼容，公共运营范围继续要求真实账户工作区。

## 原键先于限制

三个受理入口先查询原幂等记录。同键同body返回原Run/Task，同键异body返回409 `IDEMPOTENCY_CONFLICT`；之后才检查新生成权限。限制不会使受理不明的原请求失去只读核对路径。

新请求遇到限制返回403 `GENERATION_RESTRICTED`，本次没有创建Run、Task或消息节点，也没有消费报价、冻结额度或登记生成幂等键。这是确定的当前请求拒绝；若客户端先前已有受理不明请求，仍须保留先前的原body/key核对，不能据此推断先前请求也没有成功。

新报价同样会被拒绝。已获得但未消费的报价继续保留原冻结价格与有效期，却不保证受理权限；最终受理仍检查当前工作区限制。限制不改写旧报价、不扣费，也不按字符数重新估价。

## 两层检查与锁序

`App.checkGenerationAccessLocked`在原键查询后进行短事务快查，避免已受限请求继续触发外部审核或编辑素材准备。输入审核结束重新进入受理函数时，再查原键与限制；图片编辑spool在锁外准备，回锁后也先核对原键，再重查限制。

快查不是唯一保障。最终事务分别在`createRunCandidate`、`createTask`与多轮创建事务开始后取得工作区共享锁，先于会话、报价、钱包和分录锁。限制写入取得同一工作区行排他锁，串行化首次限制与受理，即使限制表尚无记录也不会漏锁。

锁顺序保持`App.mu → 控制写连接事务 → workspace共享门禁 → conversation（如有）→ quote → wallet/accounts → Outbox`。外部审核、编辑磁盘准备、bcrypt不持有这一组锁。允许的受理仍将资源、消息/上下文、冻结、幂等、审计与Outbox原子提交；数据库故障不能被解释成默认允许。正常策略拒绝使用业务错误，不把健康数据库永久熔断。

终态保存、检查点、媒体领取/续租、原handle查询、恢复和结算不调用新准入门禁，避免限制新任务时误伤既有执行责任。

## 独立角色

| 角色 | 权限 |
| --- | --- |
| observer | read |
| operator | read、case_open、investigate |
| finance | read、case_open、finance |
| moderator | read、generation_restrict、appeal_resolve |

前三种角色不自动获得限制或复核决定权限；moderator不继承财务处置和异常工单调查权限。角色可显式组合，但每项敏感动作仍在事务中重核当前账户、会话、授权和密码proof，撤销moderator后旧proof失效。授权继续由停机CLI预演、精确摘要和稳定操作键执行，不通过普通注册或工作区owner自动授予。

017扩展SQL角色与运营审计闭集；Go同步接受`generation.previewed/restricted/lifted`、`appeal.created/upheld/lifted`以及`restriction/appeal`资源类型。审计不包含用户申请正文、密码或私有证据正文。
