# V17 同一服务的持续混合验收

`TestPostgresMixedServiceSoak256` 在一个新建的 PostgreSQL schema 中启动标准 `cmd/server`，为两个账户注册并用各自全新的 CookieJar 登录。所有聊天、图片提交、状态查询、原收据和 SSE 均通过正常应用 API。模型 HTTP 对端由本次测试在环回地址创建，两个档位使用同一执行和核对逻辑。

| 档位 | 计划窗口 | 常规 / 突发 | 总量 |
| --- | --- | --- | --- |
| `pilot` | 6 个 18 秒窗口，共 108 秒 | 每窗 2 对，第 2 窗 4 对 | 14 对聊天和图片，另 1 条故障聊天 |
| `24h` | 96 个 15 分钟窗口，正好 24 小时 | 每窗 30 对，第 2 窗 60 对 | 2,910 对聊天和图片，另 1 条故障聊天 |

两个工作区按请求序号交替。投放从固定起点按截止时间计算，跳过已过期的时隙；同时待观察媒体最多 16 项。驱动逐项记录漏投的计划时刻、截止、观察时刻和原因。只有在实际 Kill 后、替代服务就绪前或就绪瞬间到期的过期时隙可以豁免；该区间之外到期的时隙和因待观察媒体达到 16 项而漏投的时隙，均使测试失败。每个普通聊天读取并核对两个内容增量及终态。图片走正式异步提交和原 handle 查询。编号 0 的查询先收到一秒 Retry-After，再按同一 handle 查回受控供应商失败，其余图片同样以已知失败收尾。收据回放必须归属原项目、使用原请求键；最终比对每个已投请求的网关 POST 次数，未投时隙必须零外发。

中间窗口有一个额外的聊天。驱动读到它已提交的第一条增量，并核对在途图片的数据库原 handle 后，终止工具刚刚启动的那个服务进程。驱动等待该进程和仍在进行的上游流退出，并从独立数据库连接确认旧代次的 PG 客户端连接归零，再用原 schema、原私有目录和新的代次观测标签启动同一二进制。通过旧会话读取恢复状态 `INTERRUPTED/PROCESS_RESTARTED` 与原前缀，再用原游标读取唯一剩余终态，回放两个工作区先前的原收据，核对网关没有重复生成 POST。

## 在专用本机数据库运行

从当前被验收的仓库根目录重新构建标准服务，报告记录实际哈希。要求 Windows、本仓库指定的 Go 版本、独占的本地测试 PostgreSQL，数据库角色可新建并删除自己的 schema。`TEST_DATABASE_URL` 由集成人在当前 PowerShell 会话设置，只接受环回 IP。服务端与模型对端均由测试创建，数据库和私有目录在两代控制器之间复用。请使用仓库既有的 PG 串行安排。

```powershell
$soakOutput = New-Item -ItemType Directory -Path (Join-Path ([IO.Path]::GetTempPath()) ("v17-soak-" + [guid]::NewGuid().ToString("N")))
$env:STUDIO_MIXED_SOAK_SERVER = Join-Path $soakOutput.FullName 'server.exe'
go build -trimpath -o $env:STUDIO_MIXED_SOAK_SERVER ./cmd/server
if ($LASTEXITCODE -ne 0) { throw "controller build failed" }
$env:STUDIO_MIXED_SOAK = 'pilot'
$env:STUDIO_MIXED_SOAK_REPORT = Join-Path $soakOutput.FullName 'pilot.ndjson'
go test -count=1 -p 1 -parallel 1 -timeout 7m -run '^TestPostgresMixedServiceSoak256$' -v ./internal/studio
```

长期档用 `STUDIO_MIXED_SOAK=24h`，将报告改为一个新的绝对路径，并将 `go test` 的 `-timeout` 改为 `24h10m`。每次报告独占创建。测试执行结束才清理本次创建的 schema。配置缺省时，该用例由 Go 明确标记为跳过。

## 阅读结果

NDJSON 逐行写入并同步到盘。配置记录含服务二进制 SHA-256、运行平台、Go 版本和档位。基线、窗口、故障和排空记录带相对单调时刻、服务代次和资源样本。假如报告中断，已写出的窗口可用于诊断；完整通过要求 Go 测试成功且最后存在 `type=summary, complete=true`，其中计划量等于投放加漏投，应用受理量等于对应终态量，上游聊天累计额外包含 1 条中断聊天。

| 数据 | 口径 |
| --- | --- |
| 计划、投放与观察 | `Planned/Offered/Missed` 按对计数。受理、首增量和终态用同一观察时刻选择窗口并计算延迟，逐窗核对样本数与计数。原键回执按实际观察时刻归窗。故障聊天的游标和原收据另计，普通受理数只含正常工作对。 |
| 延迟 | 每窗给出样本量、P50/P95/P99、最大值（毫秒，最近秩）。分别从计划到客户端发送、从发送到聊天/图片受理、聊天首个可见增量、聊天终态，以及从图片受理到首次观察到终态。图片端点按至多约 400 毫秒间隔轮询，数据包含读者观察延迟；首次观察到终态距受理超过 90 秒也判失败。 |
| 活动和通知 | 记录本窗口已受理但读者尚未观察到终态的图片峰值；数据库边界样本另计活动聊天、活动与待核实媒体、通知待投影量和留存量。最终要求活动、待核实和待投影全部为零。 |
| 进程和 GC | 服务与驱动分别读取 Windows CPU 累计毫秒、当前驻留字节及打开句柄数。服务 GC trace 仅在内存提取 STW 暂停累计毫秒、周期和解析失败数，驱动记录累计 GC 暂停纳秒和周期。服务累计值随代次重置。 |
| PG 和网关 | 每一代使用独立 `application_name`，记录该代服务连接数、执行中及等待锁数量。网关累计区分聊天 POST、图片 POST、原查询 GET、限流及无效调用。边界快照不足以推断窗内瞬时峰值。报告写出观测值，资源增长和尾延迟没有预设通过阈值。 |

图片的预期终态是受控供应商失败。真实图片交付、对象下载、权益结算、真实供应商、独立负载机、指定参考机器与高并发口径仍各自按原验收条件执行。两个固定档位仅改变同一混合用例的持续时间和投放密度。

## 本机短档结果

集成人从主树构建标准服务，通过本机实库 `STUDIO_MIXED_SOAK=pilot`。6 个 18 秒窗口实测 108.008 秒，14 对计划全部投放，14 条正常聊天完成，14 个图片任务按受控上游的明确失败收尾。另 1 条故障聊天从保留的原增量读取中断终态。原键核对聊天 17 次、图片 16 次。上游累计 15 个聊天 POST、14 个图片 POST、15 次原 GET，含 1 次受控限流，重复生成与无效请求均为 0。杀停服务到核实原收据为 869 毫秒，旧代 PostgreSQL 连接归零，排空时活动任务、活动聊天和未投影通知均为 0。 [实测窗口及服务制品散列](assets/mixed-service-pilot-040.json)
