# 2026-11-22-200 V17 工作台网络条件、冷暖启动和万条历史进入验收

## 目的

在相同的认证工作台、构建文件和真实项目资料上，实测 20 Mbit/s 上下行、80 ms 往返条件下的首个可用控件、进入万条历史以及编辑输入的耗时。首屏全部实际 JavaScript 请求都计入 300 KiB 传输预算。

## 范围

覆盖 H02 项目与会话、H08 工作台和 V17 前端性能。依赖 036 的长会话、194 的正常受理/真实环回生成、197 的 Chromium 渲染信息，以及 199 的生产静态压缩传输。正式运行必须使用包含自由画布和 199 的同一最终 Go 与工作台构建组合，制品摘要取自实测文件。

## 实际文件

- `internal/studio/network_browser_test.go` 负责从正常 API 建立一个长分支、注册真实会话、限制测试目标为专用环回数据库，并由受控子进程执行浏览器测量。
- `internal/studio/network_browser_probe_test.go` 为测试服务加入固定长度传输校准及静态 JS 响应实写计数；包含尺寸、错字节拒绝和计数验证。
- `apps/workbench/scripts/network-history-browser.mjs` 驱动独立 profile、实际项目交互和网络校准。
- `apps/workbench/scripts/network-history-measure.mjs` 与 `scripts/perf/network-history-measure.test.mjs` 核对传输、真实缓存命中和最近秩分位数。

## 接口与数据影响

专项直接使用正常 Go 工作台 Handler，所有服务在环回。一个独立测试数据库 schema 与两个临时私有目录服务整组。5000 次顺序正常受理、锁内提交、环回模型流和原聊天上下文校验生成同一分支 1 万条消息，每轮必须读回原答复，核对实际库中消息数和固定叶。浏览器从普通项目首页经真实鼠标点击导航和会话，在首个 20 条窗口中核验最后一轮双方的原 ID 与正文，输入文字后在下一次绘制机会确认输入仍在。末尾重新核验生成调用数。194 独立验收负责完整 500 页及淘汰后回读，本专题计时只涵盖进入已有历史。

正式样本数每类 20 个，按轮交替冷暖先后，每个计入样本使用全新进程、配置目录和页面上下文。冷样本直接进入项目；暖样本先完整走一次相同路径，再经空白页面重新导航，保留 HTTP 缓存、清除该一次性浏览器的界面选择和草稿。已有真实 HttpOnly 会话通过测试进程管道交给 Chromium，认证业务与会话验证照常执行。样本不包含注册、输入口令和 fixture 建树时间。后端、数据库缓冲和 OS 文件页可以跨样本复用。1920 × 1080、设备像素比 1，显式允许硬件；逐次记录浏览器版本、实际渲染器、Canvas 2D/合成状态、CPU/逻辑线程和内存。无法从实际渲染器识别集显时保留未确认。

CDP 设置 80 ms 延迟及双向每秒 2,500,000 字节；开始、中间和结束另外使用独立配置目录复测。每次校准预热后采七次同源空响应 RTT，三次下载和三次上传 4 MiB，用 SHA-256 验证两端字节。按总耗时扣除实测中位 RTT 计算有效速率。校准判断区间为 RTT 56–112 ms、上下行各 16–24 Mbit/s；它仅用于识别模拟丢失或运行条件偏离。

每份样本分别汇总点击聊天前与历史进入后的文档、JS、CSS、历史 API、其他 API 和其他站内资源的完成请求数、编码正文、解码正文、Resource Timing 传输字节和缓存命中。启动脚本逐件比对浏览器 `Content-Encoding`、`Vary`、声明长度、实际编码正文和 Go 发出的 JS 正文字节；冷样本必须有真实 gzip 传输且各次总量不超过 300 KiB，暖样本须有真实缓存命中。Resource Timing 的 transferSize 含头部估计，预算单独采用应用实际写出的编码正文。长连接单列响应头计数，尚未完成的 SSE 正文不混入首屏完成传输。相同压缩实体从缓存复用时的实体长和当次网络正文分别记录。

脚本探针为每次真实 JS GET 附上仅限本机测试的 `Server-Timing` 回执号。浏览器将每条完成的 Resource Timing 与 Go 的响应码、gzip、声明长度和已写字节逐一配对。请求开始时间与点击属于同一文档的时钟，因此点击前发起、点击后到达的脚本仍计入启动预算。两个阶段之和须与整个样本全部原始 JS 写入相符。跨阶段遗漏、重复和无对应浏览器条目的写入会使验收失败。

在真实工作台复现时，新会话起初输入长度为零；可信输入写入 6 字且已绘制。随后直接切换文档，实际 beforeunload 回调阻止离开；取消离开后，原 6 字仍在。选中仅此次产生且已核验的测试草稿、用真实 Backspace 清空，输入计数变成 2、长度变成零，随后成功进入空白页。新暖样本在预热结束后执行这段操作并记录焦点、输入长度、可信事件、清空及文档切换结果。专项不写聊天草稿到服务端或派发生成。独立校准现在优先采用 `NETWORK_CALIBRATION_REPORT`；仅单独启用该用例时仍可从 `NETWORK_BROWSER_REPORT` 读旧配置。两个用例同时启用时须指向两份不同的新报告。

## 风险与限制

本机对照中，保留旧 CDP 调节方式、只把请求正文换成浏览器原生 Blob，也实际传完 4 MiB，得到 204、耗时 1830.3 ms。新驱动在校准及工作台请求上统一应用 Chromium 的 URL 网络规则，对下载 Blob 的全部原字节验 SHA，再用同一个 Blob 上传。三组实测 RTT 均高于设置的 80 ms，落在预先固定的校准区间内。失败报告保留已完成的组和每笔原始数值、HTTP 状态、字节及摘要核对、操作/序号和仓库脚本行号；探针只补充固定数值计数。原 ArrayBuffer 与连接中断的关联有实测对照，Chromium 内部退出原因未确认。

CDP 模拟作用于浏览器 HTTP 层，实测 RTT/吞吐是该工作台同源请求的结果。本地 HTTP/1.x 环回与专用 PG、已认证会话不覆盖公网 TLS、跨区网络、真实模型、运营域名、实体手机或独立高配机。输入下一绘制机会的耗时也不等同于物理像素呈现时间。实际 GPU 分类取决于本轮浏览器数据，不沿用其他验收的硬件结论。敏感请求身份与会话文本不会写入报告。

## 回滚方式

本项将测试专用逻辑置于 Go 的 *_test.go 文件和可选浏览器脚本。撤回专项时撤回所列文件与执行入口引用，正常工作台不提供网络探针路由，业务数据库没有格式变更。

## 037 正式冷暖网络验收

本机 PostgreSQL 普通业务入口完成 5,000 轮，存储同一分支 10,000 条消息；工作台和探针在同一真实服务入口测试。Chromium 157 在 Intel Core Ultra 7 155U 集显、1920×1080 下，冷暖各 20 个独立样本。冷启动每次实际写出 166,103 字节 JS（其中入口 gzip 165,212 字节，附加分包 891 字节），低于 300 KiB；暖启动每次均为 0 字节 JS 新增传输。首个可交互点 P95 冷 880.0 / 暖 565.8 毫秒，项目点击到旧消息可见 P95 冷 834.9 / 暖 317.4 毫秒，输入到下一绘制机会 P95 冷 27.6 / 暖 28.6 毫秒。配置双向 20 Mbps、80 毫秒，三次浏览器校准实际中位 RTT 为 104.9、106.9、107.8 毫秒，下行 19.67–19.71、上行 19.55–19.63 Mbps。历史只读过程中新增模型请求为零。正式 go test 用时 323.944 秒。 完整记录见 [原始聚合报告](../wiki/assets/performance-network-037.json)。
