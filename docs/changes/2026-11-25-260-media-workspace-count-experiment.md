# 260 · 原查询保存时的工作区计数成本

## 目的

V17 核对同一原句柄多轮 GET 保存时，工作区活跃计数产生的物理日志、保存等待与端到端查询速率。

## 范围

H03、H07。A 使用原 040。B 只在本地专用 schema 的原函数中，当旧、新成员均活跃且所属工作区、provider 模式和 lane 都相同时，跳过成对的计数加减。锁顺序、任务投影和版本继续沿用 040。每档分别执行带 WAL 观测的 ABBA 和独立计时的 ABBA。

## 实际文件

[四个测试文件的补丁](../wiki/assets/media-workspace-count-260.patch.gz) · [逐档测量与源摘要](../wiki/assets/media-workspace-count-260.json) · [查询容量 Wiki](../wiki/media-original-query-capacity.md)。本台账、README 与 Wiki 导航、台账索引、V17 任务源、生成的 TODO 和推进记录同步登记。

## 接口与数据影响

使用两个正常注册的工作区、原受理入口、原句柄、真实回环 HTTP 与 PostgreSQL 持久事务。候选函数只在实验 schema 内安装，正式服务沿用 040 格式。依赖本地版本化迁移及匹配的测试程序，外部 API 和原收费边界沿用原契约。

## 验证结果

边界、24、512 三个 Go 命令分别用时 71.344、219.157、987.906 秒，三个进程均退出 0。边界两臂和两个数值档的全部物理及计时波次通过。控制器核对归属、实库设置与干净停机，报告附各档运行编号和散列。

A 使用原 040，B 在本轮临时 schema 中跳过活跃成员相同的计数更新。两组通过相同的 11 个边界检查点，每组 3 次受理、4 次查询。本轮按保存事务的 XID、表空间、数据库、物理文件和主 fork 识别 Heap UPDATE 与 HOT_UPDATE。跨页更新只计一次。实验 schema 的普通持久 heap 更新与整个事务的 WAL 记录字节分别统计。旧版探针的提交前统计含同一数据库连接前序事务的未刷出数据，旧版逐笔更新次数无法归属。

### 24 个原 handle

每波有 25 次正常受理、25 次原 POST、72 次原 GET。最后 21 项仍在轮询，3 项明确失败，1 项受理未返回 handle。重复 POST 和意外请求分别为 0、0。

物理观测组每波逐笔匹配 69 项非终态保存。每笔非终态结果均由 6 次工作区行更新降至 0 次。两对 B−A 的工作区 heap 更新数分别为 -414、-414，其余 heap 更新数的逐笔差异分别有 0、0 项。带事务标识的 WAL 记录总长各差 -125030、-125547 字节。平均每笔各差 -1812.029、-1819.522 字节。

独立计时组 A1、B2、B3、A4 的原 GET/s 为 9.597、9.535、9.597、9.534。按 B2−A1、B3−A4 配对，差值为 -0.063、+0.063 GET/s，两对速率未呈现一致的增减。A4−A1、B3−B2 的同组漂移为 -0.063、+0.062 GET/s。两对控制保存 P95 差值为 -0.099、-1.763 ms。三轮到期至写出 P95 差值分别为（+5.864、-5.559、+16.694）和（-0.365、+8.801、-1.403）ms。

### 512 个原 handle

每波有 513 次正常受理、513 次原 POST、1536 次原 GET。最后 448 项仍在轮询，64 项明确失败，1 项受理未返回 handle。重复 POST 和意外请求分别为 0、0。

物理观测组每波逐笔匹配 1472 项非终态保存。每笔非终态结果均由 6 次工作区行更新降至 0 次。两对 B−A 的工作区 heap 更新数分别为 -8832、-8832，其余 heap 更新数的逐笔差异分别有 0、0 项。带事务标识的 WAL 记录总长各差 -2827004、-2810590 字节。平均每笔各差 -1920.519、-1909.368 字节。

独立计时组 A1、B2、B3、A4 的原 GET/s 为 100.293、111.188、83.632、92.994。按 B2−A1、B3−A4 配对，差值为 +10.895、-9.362 GET/s，两对速率未呈现一致的增减。A4−A1、B3−B2 的同组漂移为 -7.299、-27.556 GET/s。两对控制保存 P95 差值为 -0.488、+4.107 ms。三轮到期至写出 P95 差值分别为（+1153.477、+360.780、-919.392）和（+2506.875、+1847.741、+858.823）ms。

物理组包含事务探针。独立计时组使用同一网关只读观察，包含三秒轮询下限、正向抖动和每次至少 200 ms 的服务。每档每种顺序只有两对，本机集中到期三轮的结果仅说明这些窗口内的表现。持续每秒到达 100 项与每秒 6,000 次原 GET 的容量验收仍待实测。

### 实验修正记录

- 首版在 24 档的预热期间退出。一次预检在门槛前仅观测到 9 个已知句柄和 1 个受理未知。测试网关给缺少句柄的 202 也返回了原查询的绝对等待期限，触发同一提交渠道的协议冷却。在第二版中，只有取得有效句柄的响应才携带这一期限。无句柄的 202 保留原正文和渠道冷却。运行编号为 `run-20261124-155358-0f29b907`。
- 第二版完成边界与 24 档。物理观测四波的工作区计数读数之和依次为 5,042、58、52、4,890。该 PostgreSQL 函数会将同一后端尚未刷出的早期事务更新与活动事务更新相加，累加快照无法还原各次保存的实际写入数。此组旧数排除出逐事务统计。对应 24 档运行编号为 `run-20261124-155821-2aa8c28e`。512 档在第一波启动后由集成人停止，控制器退出 1、数据库已干净停机，没有该轮的完整性能结果。运行编号为 `run-20261124-160249-4a8e6123`。[PostgreSQL 16.14 计数读取](https://github.com/postgres/postgres/blob/REL_16_14/src/backend/utils/adt/pgstatfuncs.c#L1540-L1556) · [事务结束时的计数累加](https://github.com/postgres/postgres/blob/REL_16_14/src/backend/utils/activity/pgstat_relation.c#L480-L486)
- 第三版首次启动（`run-20261125-095427-e835ed47`）在检查既往进程时遇到 Windows `PermissionError`，当次还未启动数据库或用例。历史 PID 已被复用。将本机控制器的存活检查改为在同一个系统进程句柄上核对创建时间和退出信号，复查旧库的停机回执后重新启动。数据库的所有权、实例身份和停机核验仍按原条件执行。
- 第三版按原保存事务的 XID 与 COMMIT 匹配 WAL。每条 heap 更新按表空间、数据库、物理关系、主 fork 与操作类型归属，跨页更新只计一次。提交前观察的耗时、完整控制保存的耗时和未插入物理观测器的吞吐分别报告。[PostgreSQL 16.14 的更新块登记](https://github.com/postgres/postgres/blob/REL_16_14/src/backend/access/heap/heapam.c#L8460-L8479)

### 集成结论

保留 040。512 个原句柄的两轮配对中，候选每轮在 1,472 笔非终态保存上少写 8,832 次工作区行，按事务标识归属的 WAL 分别减少 2,827,004 和 2,810,590 字节。相同任务数量下，候选相对原实现的吞吐一次增加 10.895 次原 GET/秒，一次减少 9.362 次，同一候选自身两波相差 27.556 次/秒。第二对的三轮到期至写出 P95 均延长，分别增加 2.507、1.848 和 0.859 秒。24 个句柄也只观察到一升一降。证据支持减少写入，尚不足以用新格式替换现有查询路径。后续沿原保存事务单独计量待投递事件的去重、项目序号、写入与待投递数耗时，再决定是否值得调整。

### 复测方式

在具有报告中主树输入的独立工作副本中解压实验补丁。解压后的 SHA-256 应为 `79e6beeb8a02375b1da5065b8e5a3a16c1df6e462c0636fb77383343795ebc13`，gzip 文件的 SHA-256 为 `570cbadee9790c7d2c7c5f3dd39236b733cc80035f828359100844aa11379328`。先运行 `git apply --check --whitespace=error <补丁路径>`，再在该副本应用。实验只改变报告列出的四个 `*_test.go` 文件。

使用 PostgreSQL 16.14 和对应版本的 `pg_waldump`。服务端配置启用 fsync、同步提交和整页写入。将 `TEST_DATABASE_URL` 设为允许创建独立测试 schema 的本机回环测试库，将 `STUDIO_MEDIA_COUNT_PG_BINDIR`、`STUDIO_MEDIA_COUNT_PGDATA` 和 `STUDIO_MEDIA_COUNT_PG_SYSTEM_ID` 设为同一测试实例的工具目录、数据目录和集群标识。两档的 `STUDIO_MEDIA_COUNT_REPORT_260` 均为尚未创建的私有文件绝对路径。以 PowerShell 串行执行下列命令，`$privateReportDir` 指向预先选定的私有报告目录。

```powershell
$env:STUDIO_MEDIA_COUNT_260 = '1'
go test -p 1 -parallel 1 -count=1 -v -timeout 8m -run '^TestPostgresMediaCountBoundaries260$' ./internal/studio
if ($LASTEXITCODE -ne 0) { throw '260 boundaries failed' }
$env:STUDIO_MEDIA_COUNT_PASS_260 = 'both'
foreach ($tier in '24','512') {
    $env:STUDIO_MEDIA_COUNT_TIER_260 = $tier
    $env:STUDIO_MEDIA_COUNT_REPORT_260 = Join-Path $privateReportDir ("260-" + $tier + ".json")
    go test -p 1 -parallel 1 -count=1 -v -timeout 48m -run '^TestPostgresRecurringMediaCountABBA260$' ./internal/studio
    if ($LASTEXITCODE -ne 0) { throw ("260 tier failed " + $tier) }
}
```

## 风险与限制

每种数值档仅有两对无物理探针的计时比较；工作区竞争、检查点、整页写入、首轮到期分布和进程 GC 会影响结果。单机三轮原查询与已知失败终态只覆盖本机测量范围，真实供应商限额、固定部署每秒 6,000 次原 GET、24 小时混合运行和成功交付须各自验收。

## 回滚方式

正式实现仍使用 040。复测使用独立工作副本、测试 schema 和私有报告，结束后沿用原服务制品与数据格式。
