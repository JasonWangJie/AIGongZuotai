# 209 不同 Run 的公开增量共用持久提交

## 目的

V17-J2 在现有业务流上减少 PostgreSQL 事务数。单个事务可以为多个正在执行的 Run 各追加一个公开增量，原租约、序号和提交确认继续决定这次追加是否有效。

## 范围

H03 聊天执行、H07 持久事件。209 提供数据库追加与故障专项。210 负责协调器、开关和确认后通知，211 通过实际工作台业务比较开启和关闭时的结果。数据库使用 037 已有格式。

## 实际文件

- `internal/studio/run_delta_batch_store.go` 实现有限组批、锁定、分类、批量追加、确认和逐项结果。
- `internal/studio/run_delta_batch_store_test.go` 检查输入、物理事务、公开前缀、租约、审核、幂等、输出和保留窗口。
- `internal/studio/run_delta_batch_fault_test.go` 检查持锁取消、自然到期导致整组回滚、服务器明确回滚及丢失提交应答。

## 接口与数据影响

`appendRunDeltaBatch` 接收同一控制代次内不同 Run 的租约、原期望序号、增量和发生时间，结果顺序等于输入顺序。最多 32 项、累计 256 KiB。单项仍须符合原 128 KiB 输出预算和 UTF-8 要求。事务依次获取控制代次共享锁、有序业务行锁、有序流头锁。忙行交给原单条路径，其他已取得锁的行可先提交。

每条候选均比对 owner、epoch、generation、execution、活动状态、审核门禁、水位和输出预算。一次 SQL 通过数组插入原事件并更新各自流头。修订落在已覆盖检查点时可一并清除刚过期的一条旧事件。需要重建检查点、超过窗口字节预算、核对旧序号的重复输入等场景仍调用原存储逻辑。数据库最终按同一时刻复核全部快路径租约，之后才提交。

正常返回的三个计数分别为确实提交且含新事件的批事务数、这些事务确实新增的事件数、实际调用原单条路径的次数。事务尾有租约到期时，先得到整组回滚确认，再将到期者标记失权并对其他项执行原单条追加。写语句收到服务端 `40001`、`40P01`、`55P03` 且回滚已确认时也允许逐项处理。提交应答丢失沿用原控制写者失效保护，等待者收到数据库不可用；可从原库读取已确认的公开前缀。

## 验证结果

037 隔离源码内运行 `go test -count=1 ./internal/studio -run '^TestRunDeltaBatch' -v` 通过，0.166 秒，含真实 PG 专项编译。以下命令由集成人在本机专用 PostgreSQL 测试库串行执行。

```powershell
go test -count=1 -timeout=3m ./internal/studio -run '^TestPostgresRunDeltaBatch' -v
```

六项专项分别验证物理提交与逐项授权、保留窗口与输出上限、并发取消、写入后自然失期、写语句明确回滚、物理提交后丢 ACK。独立数据库连接核对事件的 `count(*)` 与 `count(DISTINCT xmin::text)`。回滚专项用测试 schema 内的序列记下尝试事务号，再查 `pg_xact_status`；事务号不进入产品记录或报告。真实业务提交节省和客户端耗时以 211 的同负载对照为准。

## 风险与限制

计算租约截止时使用事务尾的数据库时钟。实际提交与网络答复仍需耗时。原单条路径的 5 秒数据库超时在取得控制写连接互斥后计时，组别最多可另有 32 次逐项操作。等待协调器、取得写连接及依次处理回退均计入调用方实际耗时。某项等锁时，正常同组项可以已物理提交，调用方需等逐项结果返回。未知提交停写，恢复读取原身份及公开前缀。209 的数据库专项只涉及测试数据，真实授权 SSE、向模型请求次数及容量需在 210 和 211 联合验收。

## 回滚方式

由控制器停用 210 协调器，使新追加通过原单条路径。已落库的事件和流头可由原格式读取、继续和恢复，无须改数据库表、清理日志或重投原生成请求。
