# 262 · 原 GET 进度保存的 Outbox 分段耗时与事务归属

## 目的

量化真实原句柄 GET 返回后，RUNNING 任务更新事务内各步骤的耗时，并核对任务版本与项目 Outbox 事件在 PostgreSQL 中的事务归属。

## 范围

V17、H03、H07。沿用已验收的 257 原查询夹具。两个正常注册的工作区分别持有自己项目的原任务。查询执行位配置 128，租约连接数 4，回环网关原 GET 服务时长配置 200 毫秒。净计时、分段、物理、分段、净计时各使用一个新 Go 进程与测试 schema。

## 实际文件

两份实验补丁均含 `internal/studio/media_query_recurring_test.go`、`internal/studio/outbox_measure_262_test.go`、`internal/studio/outbox_trace_262.go`。分段补丁另外在 `internal/studio/persistence.go` 和 `internal/studio/outbox.go` 的原事务调用处接入时间戳。压缩包保留已实跑的补丁字节，正式业务源文件和数据库迁移沿用原版本。[净计时与物理观测补丁](../wiki/assets/media-query-outbox-262-040-base.patch.gz) · [分段计时补丁](../wiki/assets/media-query-outbox-262-040-profile.patch.gz) · [逐工作区与全样本数据](../wiki/assets/media-query-outbox-262-040.json)

## 接口与数据影响

正常 HTTP 受理后只读取原网关句柄。每次保存按两个已登记的原工作区、项目、任务、事件键和资源版本核对。物理观测的触发器及见证表仅建在该轮私有测试 schema 内。公开附件只保存聚合耗时、计数、程序版本及补丁/报告摘要。正式 API、Outbox 事务、配额和存储格式继续沿用 040。

事务从发出 BEGIN 前量至收到成功 COMMIT 后。分段包含相邻 Go 调用之间的开销；应用状态锁和控制数据库连接互斥锁的排队发生在该区间之外。

每轮的 25 次原受理中，24 项获得句柄，1 项无句柄且保留受理未知状态。24 个原句柄各查询三次，共 72 次原 GET。末轮 21 项仍在运行、3 项明确失败；69 笔 RUNNING 保存分属于两个工作区（33、36）。

物理轮在测试 schema 对 Outbox 新事件执行 AFTER INSERT，以当前任务版本、实际事件的 scope、资源版本和原状态匹配并当场比较两行 xmin。独立查询核对全部 69 笔匹配后才计入。项目事件后续投递可形成新行版本。

五个 Go 进程各自通过指定专项并退出 0，使用同一原 PostgreSQL 实例、独立测试 schema。每轮新增子进程均已收回，最终控制器、工作进程和原 PostgreSQL 均已退出，库干净停机。

### 工具与复测

Windows/amd64、Go 1.26.11，GOMAXPROCS 为 14，PostgreSQL 16.14 开启 fsync、synchronous_commit 和 full_page_writes。原验收对每轮运行 `go test -json -p 1 -parallel 1 -count=1 -timeout=3m -overlay <该轮配置> -run '^TestPostgresOriginalOutboxProfile262$' ./internal/studio`；核对测试通过事件、真实退出码和报告散列后才进入下一轮。受测主树输入 SHA-256 为 `65451f388783835bf2dd8338b684f33e1e61b66117abdcf916f303ba6f32ab00`。

复测时在两份独立、匹配的测试副本中分别解压、核对散列并应用一份补丁。净计时和物理两类使用 base，分段使用 profile；设置 `STUDIO_OUTBOX_262` 为 `clean`、`physical` 或 `profile`，`STUDIO_OUTBOX_REPORT_262` 为本轮新文件。使用自有可建 schema 的回环 PostgreSQL 测试库并传入 `TEST_DATABASE_URL`。直接应用补丁的副本可用相同 Go 参数省略 `-overlay`。复测顺序与上表一致。

### 集成人结论

两次分段中，原 GET 返回后保存任务的事务平均耗时分别为 6.70 和 7.49 毫秒。事件去重后的四次数据库调用分别占每笔 0.84 和 1.02 毫秒，值得用独立候选检验合并往返的实际收益。大部分时间仍发生在进入 Outbox 之前，两轮分别占 76.54% 和 76.66%。正式服务继续使用 040。候选须分别验证首次项目序号、重复事件、容量耗尽回滚、任务与事件同事务，再与原实现在相同并发和到达率下比较。

## 风险与限制

原 GET 窗口包含回环 HTTP 时长、业务调度和原夹具的服务端状态查验；分段位于 SQL 调用外侧，物理轮额外写见证表。净计时两轮仅记录本机小档基线。更高并发、真实供应商、固定环境持续每秒 6,000 次原 GET 和 24 小时混合运行各需独立实测。

## 回滚方式

复测结束后由夹具按既有流程清理该轮私有 schema，丢弃两份实验副本。正式服务继续使用原 040 程序和数据格式。
