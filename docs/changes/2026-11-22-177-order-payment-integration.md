# 177 · 订单资金、购入权益和联备后读回

## 目的

验证购买意向、可信资金事实和权益分录能够独立核对。确保用户可以在浏览器查看自己原单的实际状态，并能在恢复后继续核对同笔退款和原入账。

## 范围

V13-B2 只在受控本机测试库向包内事务入口提供合成的已认证事件；普通用户页面与 API 只读状态。覆盖 H01、H05、H06、H08、H09。正式渠道认证、权威支付查询、出款、退款规则与实商户另验。

## 实际文件

- `internal/studio/order_payment_integration_test.go` 用两个真实登录账户、两次独立购入和一笔部分退款驱动 Chromium，再停写备份、恢复到新库并重放原通知。
- `internal/studio/order_intent_http.go` 注册本人只读资金状态；`order_reconciliation.go`、`storage_maintenance.go`、`operations_admin.go`、`ledger_admin.go`、`storage_maintenance_delivery_test.go` 同步 035 精确版本。
- 035 数据模型、同一经济事件归并及单笔权益见 174。HTTP 与 OpenAPI 见 [175](2026-11-22-175-order-payment-status-http.md)，工作台与浏览器程序见 [176](2026-11-22-176-order-payment-workbench.md)。
- `docs/wiki/decisions/0035-order-payments.md`、迁移说明、README、Wiki、台账和规划登记实测与真实商户边界。

## 接口与数据影响

新增 `GET /api/v1/order-intents/{order}/payment-status`。原意向和 033 原收据保留原始含义。035 资金事件与购入权益同事务受理，原支付、后续退款和权益处理分别展示。原意向已有资金证据时，新的普通取消拒绝。真实退款不会自动从其他购买额度或生成冻结中扣款。

## 验证结果

集成人在准备镜像编译真实 PG、Chromium 和联备程序，`go test -count=1 ./internal/studio -run '^TestOrderPaymentStatus'` 通过，0.218 秒。固定版本的真实 PG 专项、累计回归、两账户查看状态及恢复结果在实际运行后记录。

## 风险与限制

测试身份认证和 PostgreSQL 均为真实本机组件，测试支付通知为合成样本。正式商户签名、商户账单、真实支付及退款需要指定渠道。真实履约和部分退款政策尚待明确，本批不推断收入确认或真实退款完成。

## 回滚方式

如需恢复 034 行为，停止写入，在独立目标还原升级前整套 034 联备并使用匹配制品。保留 035 资金事实和权益分录以便核对，禁止清除绑定、journal 或迁移登记来降低格式。

## 时间边界复核

035 首轮 16 项金融及维护专项共 72.222 秒，退款早于原款的本人状态断言失败，其余 15 项通过。浏览器与新库恢复用时 13.68 秒。测试曾把 Go 主机时钟与 PG 的绑定/接收时刻混用；在本机对 500 次只读时钟采样，476 次数据库时间晚于客户端接收时刻，最大 604 微秒。原 HTTP 用例单独再跑四次均通过（15.132 秒），原失败未保留逐项状态。合成的已认证通知现统一从 PG 取时间，显式测试未来/早于绑定的输入继续按原业务规则待核。

## 035 本机专项复验

集成人在固定 035 工作台、真实本机 PostgreSQL、Chromium 和 FFmpeg 上串行执行 17 项，全部通过（82.279 秒）。20 个独立数据库连接竞争同一经济交易的用例 3.55 秒，取消与收款两种顺序 2.64 秒，丢失提交应答并重启 2.73 秒，034 升级保留客服、意向和账本 2.23 秒。收款/退款、已花/冻结及其他购买的保护，权益容量不足、等待席位、身份冲突和精确维护栅栏均通过。 两账户实际网页及迁库重放 16.55 秒；[390 像素下的合成部分退款与原权益](../wiki/assets/order-payment-mobile-035.png)。资金通知均为本地测试输入。

随后在同一固定制品上再串行两轮，实际本人状态接口分别 3.72 和 3.98 秒，真实视频浏览器分别 21.34 和 22.48 秒，合计 51.669 秒，四次均通过。

## 联备恢复后原退款的逐表复核

`TestPostgresOrderPaymentBrowserAndPairedRestore` 沿用 173 的签名函数。恢复后重复提交同一份原退款通知，分别在提交前后以只读可重复读事务计算 18 张表的全行签名，覆盖意向、原收据、原七张权益表，以及 035 的环境、绑定、经济身份、资金事实、通知、冲突、购入权益、待核原因与等待席位。本人原有部分退款状态也必须与重放前相同。两个摘要集合只在测试进程内比较，诊断使用固定描述。此前 16.55 秒为原范围的实测结果，18 表扩展的真实 PG、浏览器和迁库重放由集成人另行登记。

## 固定 035 累计验收

固定 035 完整回归通过，629 个顶层用例，零失败、零跳过。studio 包 1670.146s，视频导出包 2.669s。实际启用 PostgreSQL、版本化本机对象存储、真实 Chromium、FFmpeg、十万调度积压、二十万旧任务迁移和编译出的只读订单核对命令。该制品的 553 项工作台测试、157 模块生产构建、Go vet 和六套冒烟均通过。

## 035 十八表资金复核

累计运行结束后，集成人在同一 035 服务和工作台上串行复验扩大后的两项断言。先写入真实隔离 PostgreSQL 的合成收款、同额退款及唯一购入分录，再用编译好的只读核对命令检查业务。核对前后 18 张订单、权益及资金表的所有行摘要一致（3.12 秒）。真实 Chromium 与新库恢复后重放原部分退款，18 表和本人状态也保持一致（12.91 秒）。两项合计 16.178 秒，未使用真实商户。
