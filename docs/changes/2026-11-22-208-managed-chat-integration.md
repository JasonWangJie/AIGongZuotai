# 208 受管聊天执行集成

## 目的

V17-J1 把模型 HTTP 执行分给本机子进程，并在真实工作台路径上验证超过原有 64 个聊天执行位。原有 64 路基线见 [201](2026-11-22-201-active-stream-capacity.md)。

## 范围

覆盖 H02、H05、H07。父进程保有数据库控制锁、会话受理、统一配额、审核、权益、执行租约、输出确认和公开 SSE。操作系统子进程只处理来自匿名管道的冻结模型请求。

## 实际文件

传输、调度与测试的实现分别见 [205](2026-11-22-205-chat-execution-child-transport.md)、[206](2026-11-22-206-managed-chat-scheduling.md)、[207](2026-11-22-207-managed-chat-acceptance.md)。集成文件包括 `cmd/server/main.go`、`.env.example`、`scripts/lib/process.mjs`、`README.md`、`docs/wiki/README.md`、`docs/wiki/execution-scheduler.md`、`docs/wiki/decisions/v17j1-managed-chat-execution.md`、任务源、生成 TODO、进度和台账索引。

## 接口与数据影响

通过两个可选服务端配置项指定托管进程数和每进程槽数，普通本机冒烟剔除宿主的这两个值。工作台继续走既有聊天和 SSE 接口，数据库应用格式保持 037。调度在已有租约中记录当前执行 owner，以固定聚合指标反映就绪、占用和分派。已领取任务失联会保留确认前缀，用户可按原键只读核对。

## 验证结果

组合后的 `go vet ./cmd/server ./internal/studio` 和标准服务构建通过。定向配置、调度和私管道测试在主工作树运行，两个包分别通过。Windows 上两次以大小写不同的宿主变量启动隔离子进程，均确认受管设置已从其环境剔除。205 的独立 OS 测试与 207 的 PostgreSQL 联合验收分别记录；截至本条初建，集成人尚在等待前一轮全量 PostgreSQL 回归退出。

## 风险与限制

父进程、数据库控制写者和本机资源仍是共同故障域。配置值需要满足可用上游和工作区额度。进程之间可能同时失联，父端只会让仍从未领取的会话在旧本地容量内首次执行。真实供应商、跨主机、万活跃和生产高可用仍由各自验收项跟踪。

## 回滚方式

停止接纳新的受管执行，排空或依原语义中断已有工作。确认父服务及其受管子进程全部退出，在同一兼容格式的服务中省略两项受管配置后再启动。使用已确认的持久状态和原幂等键核对，不重新生成受理不明的请求。

## 集成人串行 PostgreSQL 与标准制品结果

标准服务在本机启动两个受管子进程，Windows TCP 归属与 PostgreSQL 租约分别核实每个子进程同时持有 40 条模型连接。5 个工作区各 16 条，4 个冻结模型各 20 条。80 个正常授权读者共读到 960 个原序增量，80 笔运行完成结算；模型写出到普通 SSE 读完的 P50/P95/P99 为 33.91/64.86/976.40 毫秒。另一个读者暂停约 2.07 秒。 排队取消未请求模型，已开始取消和单子进程或控制器故障的已执行运行进入 REVIEW。两个子进程全失时，只将两个尚未领取的排队请求交给控制器的一个执行位。含故障场景的标准制品共发出 87 次模型请求；隔离的审核测试宿主另发 1 次，屏蔽决定留下的候选公开增量为 0。两部分合计零额外或重复模型 POST。4 路试跑包 26.646 秒，正式档包 29.582 秒。 [正式报告](../wiki/assets/performance-managed-chat-037.json)。
