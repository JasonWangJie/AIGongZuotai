# 246 · 多工作区媒体任务正常准入与原句柄重开核验

## 目的

V17 的规划样例包含 60,000 个媒体在途任务。既有 241 对预置原句柄测量调度与查询。本项通过真实账户从工作台 API 创建任务，检查使用者配额、提交不明、实际在途数量和重开后的原请求身份。

## 范围

属于 V17 / H03、H07 的本机容量验收程序。使用 PostgreSQL 单控制写者、服务端冻结的原生图片和视频 HTTP 适配器、真实会话、同一库的私有目录。账户经正式注册接口创建，分别持有自己的项目和工作区。保留原有注册节流，大档在第十个账户后等待完整的 15 分钟窗口。供应商接收端仅绑定临时回环端口。SQL 观察连接只读业务事实，所有任务经正式受理和后台生产调度创建。

## 实际文件

- `internal/studio/media_admission_capacity_test.go` 提供显式容量档、正式 API 驱动、回环协议接收端、双阶段持久身份核验和仅含聚合数字的输出。
- `docs/changes/2026-11-23-246-normal-media-admission-capacity.md` 登记方法和实际验证。

## 接口与数据影响

每个工作区先用图片任务填满模型配额，再用视频任务填满工作区配额。两次额外 `POST /api/v1/tasks` 均应返回对应的 429。各账户随后按完整原正文、原键和原项目重放全部请求，核验同一任务及 `Idempotency-Replayed`。普通生成以 `GET /api/v1/tasks/{id}` 读取当前状态，使用 `GET /api/v1/runtime` 核对每个工作区和模型的实际占用，另用其他账户读取原任务核验 404。

本机网关对一条 POST 返回无句柄的 202。后台应保存 `SUBMIT_UNKNOWN`，配额查询仍应计入此任务。其余 N−1 条通过原生 POST 取得各自的唯一句柄，再以真实 GET 转为 RUNNING。观察连接逐项核验任务、工作区、项目、模型、幂等收据、上游原键、正文 SHA-256、原句柄及其供应商身份。在停完第一个 App 后，以相同的库、私有目录和密钥重开，重放全部请求，核对原有账户权限、占用及状态，等待至少一次原句柄新 GET，结束时要求两次 App 生命周期内上游 POST 合计 N 次，重开后新增 POST 为零。两个 App 在同一个 Go 测试进程中依次打开，包含控制写者交接和会话沿用。

## 风险与限制

大档显式运行，持续消耗本机数据库和磁盘，60,000 档会创建相应数量的任务、收据、审计和事件。每个任务占一个额度，无句柄未知任务持续占位。测试全程无生成收费，未启用 CREDIT、邮件、审核、聊天和对象存储。已知句柄保持运行状态，用于测在途准入。每工作区顺序提交、单回环渠道和无图像/视频交付限制了可外推范围。供应商账户配额、6,000 查询/秒、多控制实例、进程强杀和 24 小时稳态有各自的验收条件。

## 回滚方式

撤回本项测试文件和相应导航变更即可。服务启动、HTTP 协议、生产调度和数据库格式保持既有行为。本项使用正式迁移初始化测试 schema，正常退出时由原有测试框架清理该 schema 及测试私有目录。

## 集成人逐档实测

040 的 128 档（12.54 秒）与 512 档（24.18 秒）均通过。均通过 4 个独立认证工作区提交，配额满时验证模型与工作区的不同拒绝。512 档在 3.036 秒完成首次受理与溢出核对；511 条 RUNNING 持有原 handle，一份受理不明无 handle 仍占位。前后各重放 512 个原键，重开后增加一次原 GET、零上游 POST。[分档报告](../wiki/assets/media-normal-admission-040.json)

4,096 档实际运行 103.28 秒。4 个登录工作区各持 1,024 项，正常首次受理及溢出核对耗时 77.652 秒。重开前后各验证全部 4,096 个原键，原任务总数不变、4,095 个原 handle、1 个无 handle 的未知状态，新增原 GET 1 次，新增原 POST 为 0。
