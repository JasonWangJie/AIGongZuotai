# 096 · PostgreSQL Run 流水位、增量与事务快照

## 目的

让进程重启后仍能读到已经确认提交的公开聊天正文，并让断线读者能按原 Run 序号继续读取。数据库同时保存可恢复的正文前缀、已提交的事件上界以及当前可回放窗口的下界。

## 范围

V16-B1，涉及 H02/H03/H04/H09。承接 [095 设计](2026-11-21-095-durable-run-stream-plan.md)，覆盖普通与多轮 Run 的 PG 受理、首次执行授权、增量保存、终态与运营快照、窗口裁剪、冷读和恢复。执行入口及 SSE 读取各有对应子项。当前以单控制写者和单次执行授权为前提。

## 实际文件

- `db/migrations/021_run_stream.sql` 创建 `studio_run_streams` 和 `studio_run_stream_events`，分别存储每个 Run 的流状态和保留事件。旧 Run 沿用原检查点，新创建的 Run 在受理事务登记流状态。
- `internal/studio/persistence.go` 在受理、开始、恢复和终态事务中接入流状态。共用的 Run 保存入口也覆盖运营核实与离线权益的已提交账务快照。
- `internal/studio/run_stream_store.go` 实现 Run 执行身份校验、提交水位、重复增量核对、快照覆盖、裁剪和前缀重建。`internal/studio/repository_queries.go` 的 Run 冷读在同一个只读可重复读事务中取得业务文档与后续增量。
- `internal/studio/run_stream_store_test.go` 覆盖写入冲突、字节预算、事务快照、审核公开和终态后正文保护。本文记录存储子项。

## 接口与数据影响

启动模型请求前，业务运行状态、首次执行身份以及适用的权益更新与项目 Outbox 同事务提交。每个非空公开增量只写一行，按 Run、执行身份和前一已提交序号核验。窗口内重复提交相同序号与原内容必须一致。公开正文上限为每个 Run 128 KiB；每个 Run 的回放窗口最多保留 256 条事件和 1 MiB 负载。裁剪将移除尚未被业务快照覆盖的增量时，同事务先物化完整前缀。正文回放和项目通知使用各自的序号。

启用输出审核时，增量写入入口拒绝该 Run 的正文。只有完整审核决定、公开业务快照和终态事务确认后，才有可读的批准正文。后续账务修订沿用原终态及原正文。021 Run 恢复为 INTERRUPTED 时从已提交水位推进一个序号；旧 020 Run 保留易失流的恢复序号间隔。

## 风险与限制

每个公开增量推进一次事务，慢存储会占用现有聊天执行位。本子项按 UTF-8 字节限制正文和事件负载，并沿用 PostgreSQL 文本字段对零字节的限制。日志窗外的游标须回读最新业务快照。B2 仍需验证独立执行租约、失权和跨连接竞争；综合混合负载、生产容量及外部渠道等待对应批次。

## 回滚方式

联备升级前的 PG、私有目录及已启用的独立密钥。需要回到 020 时，停机后整套恢复升级前的匹配备份和相应程序。021 新 Run 的已提交公开前缀可能跨业务文档与增量表；回滚前应明确升级后新受理数据的处置范围。保留迁移登记与目录归属。
