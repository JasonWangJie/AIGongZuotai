# 212 真实工作台增量批量提交集成

## 目的

在 V17-J2 中验证正常聊天的数据库提交能否合并，并保持每个运行自己的确认、可见性与回放顺序。

## 范围

修改 H05/H07 的可选 PostgreSQL 增量写入路径。独立日志 PoC、原单条写入和带业务鉴权的批量追加分别计量。受审候选仍留在原审核路径。

## 实际文件

存储、调度和验证文件分别列于 [209](2026-11-22-209-batched-run-delta-store.md)、[210](2026-11-22-210-run-delta-coordinator.md)、[211](2026-11-22-211-batched-delta-acceptance.md)。集成人同步根 README、Wiki 导航和 021 增量决策、进度、任务源、生成 TODO 和台账索引。

## 接口与数据影响

`RUN_DELTA_BATCHING_ENABLED=true` 启用跨运行分组。每个 Run 同时最多一条待确认增量，每组最多 32 个运行、256 KiB 正文。继续使用原 021/022/037 表、原执行身份、原租约和原序号。浏览器与受管子进程按各条的实际存储结果分别得到确认。

## 验证结果

209–211 的各项非 PG 测试与覆盖面见对应记录；独立工作区的编译与测试不代替整合后的真实事务。真实 PostgreSQL 在前序全量任务退出后串行执行，正式比较采用实际事件行的事务标识。

## 风险与限制

不同运行共享一次 COMMIT 的确认结果。提交应答不明时不能向浏览器公开未确认正文，也不能以新的尝试替换原记录。已确认健康项可能等待同次调用中旁路项的单独处理，故障场景与正常负载分别记录。24 小时、公开服务和万条实际模型连接另验。

## 回滚方式

在维护窗口按原语义排空或中断运行，停止旧进程，关闭开关后重启同一兼容格式的制品。原库已确认的事件继续使用同一授权 SSE 和原游标读取。

## 集成人串行 PostgreSQL 结果

本机 PostgreSQL 的两组独立新 schema 各运行 64 条正常模型流，每条 12 个增量。开关两侧各有 768 条增量按原序通过授权 SSE 和数据库回放，模型请求各 64 次。事件行的 xmin 显示，关闭时为 768 次写入事务，开启时为 24 次，每次包含 32 个不同 Run，少 744 次（96.875%）。从模型写出前到普通客户端读完相应 SSE 的 P95 分别为 52.28 和 6.83 毫秒，P99 为 73.50 和 8.10 毫秒。在本机控制的 12 个波次下测得，事务计数只覆盖增量插入。8 路试跑 26.606 秒，64 路含业务边界专项共 28.722 秒。 六项原库专项全部通过，共 13.794 秒，覆盖同事务分组与逐项授权、保留窗口与输出上限、并发取消、失期回滚、服务器明确回滚和提交应答丢失后的停写。 [业务报告](../wiki/assets/performance-batched-deltas-037.json)。
