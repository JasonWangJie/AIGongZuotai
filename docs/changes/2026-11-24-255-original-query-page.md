# 255 · 原任务查询预选的公平页对照

## 目的

V17（H03/H07）在 040 大档原 GET 调度中，对照减少数据库往返能否提高端到端吞吐。已有 249 服务作为对照。

## 范围

候选在超过 32 个查询位时，用同一条 SQL 读取最多八个投影、任务租约与冻结渠道。预选仍在现有公平游标和事务内，提交后才预留工作区预算并严格领取。32 位档使用相同的旧路径，作为对照。此次实测后正式服务保留旧实现。

## 实际文件

[逐档数值与源码散列](../wiki/assets/media-query-page-255.json)、[实验补丁](../wiki/assets/media-query-page-255.patch.gz)、本台账、容量 Wiki、README、台账与 Wiki 索引、任务源、生成 TODO、推进记录。归档补丁含候选 Go、定向用例与试验说明。

## 接口与数据影响

生产工作区没有合入候选代码。外部 API、040 迁移、原渠道冷却、单探测和原句柄的严格领取沿用既有实现。实验使用独立本机 PostgreSQL 16.14 与 200 毫秒环回服务。

## 验证结果

- 首次启动测试数据库时，Windows 子进程持有 pg_ctl 的输出管道。核对实例身份及零业务连接后正常关闭，修正测试启动器的输出重定向。该次未执行业务测量。新启动器核对原库身份、设置和此前干净停机后运行。
- 集成人串行执行 `TestPostgresOriginalQueryPage255`、`TestPostgresOriginalQueryPageCommitUnknown255` 与三项原交接、保存和确认不明用例。候选五项通过，原服务三项通过。五个对照页的原 SQL 往返分别为 14、11、9、15、11，候选均为 9。新冷却和游标提交回执丢失时均遵守原外发边界。
- 原服务 A、候选 B 按 A→B→B→A 顺序，各运行 248 开启分段计时的三档与心跳，再独立运行 `STUDIO_MEDIA_QUERY_CURVE=1` 的原查询三档。每一轮每档计划 512 项，实收 512 次唯一 GET，零生成 POST，全部排空。
- 64 位档 A 两轮分别完成 170.20、166.68 次/秒，B 为 153.65、104.71。128 位档 A 为 170.69、171.25，B 为 140.57、128.53。128 位到期至写出 P95，A 为 986.61、1,113.11 毫秒，B 为 968.73、1,523.23 毫秒。减少往返没有带来可重复的端到端收益。

复测时使用隔离的 249/252/253 源码与本机测试 PG，按报告校验实验补丁的 SHA-256，先在独立副本检查能否应用。两版分别执行 `STUDIO_MEDIA_QUERY_TIMINGS=1` 的 `TestPostgresQueryStage.*248` 和 `STUDIO_MEDIA_QUERY_CURVE=1` 的 `TestPostgresOriginalQueryRateCurve040`。

## 风险与限制

每种配置只有两轮，32 位相同路径在第三轮出现明显波动。完整窗口数据保留，不据此推断单条 SQL 的普遍性能。短时受控终态负载、持续多轮 GET 和真实供应商限额分别验收。

## 回滚方式

本轮仅登记实验结论，服务继续从原查询路径运行。独立复测副本可以恢复其原服务制品。
