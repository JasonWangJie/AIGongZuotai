# 248 · 原 handle 查询的分阶段占用与等待

## 目的

V17（H03/H07/H08）040 对照中，128 个查询位共享 4 条 SQL 连接时达到每秒 159.41 个持久终态。作用域占位曾达 128，而本机上游同时收到的 GET 最多 88。至少一次采样中有 40 个已占位执行处在 HTTP 接收端之外。为区分这些时间，248 在原运行路径采集调用边界。

## 范围

同机 PG、同一冻结渠道、每档 512 个原 handle，每秒 320 个到期，上游服务每项 200 毫秒。32 个执行位走既有 worker，64 和 128 个走 040 有界派发。三档均沿用四条查询租约连接。另有一个独立慢 GET 验证在途心跳。测试显式开启计时，普通服务没有打开采样的接口或环境开关。

## 实际文件

- `internal/studio/media_query_timing.go` 定义固定阶段和定时回调，`app.go`、`task_leases.go` 提供内部注入及本次查询租约的传递。
- `internal/studio/task_leases_worker.go`、`task_query_pool.go`、`persistence.go` 在实际选择、领取、交接、续租、结果等待和控制写事务上采集时点。
- `internal/studio/media_query_curve_test.go` 复用 040 负载，`media_query_timing_test.go` 汇总样本并核对数量、重叠、截窗、容量及独立心跳。
- `docs/wiki/media-original-query-capacity.md` 记录执行入口、指标含义与嵌套关系。

## 接口与数据影响

定时回调仅接收固定阶段、开始和结束时间。SQL、参数、任务或渠道身份、请求、响应及正文均不进入计时回调。每阶段最多 8,192 个已完成区间，溢出使测量失败。默认不建立采样器、保留样本或增加执行协程。沿用 040 数据格式、控制写者、原 handle GET 和全部原权限。

公平预选分别记录取得候选与空返或出错，严格领取分别记录成功和未领取。首次续租与真实心跳分别统计总时长，二者的连接池等待和 PG 事务另计。收到已知结果后，应用状态锁等待在取锁后立即截止。总保存包括状态入库、缓存更新及事件发布，其中控制写互斥等待在取得控制连接锁后立即截止，事务计时覆盖开始至提交或回滚、账务与 Outbox。所有时点按同进程时钟采集。

每档以首次预定到期至独立 PG 查询确认全部终态作为墙钟窗口。先结束窗口再停止工作线程并等候已开始的观测结束。按阶段输出次数、完整样本累计耗时、P50/P95/P99、窗口内的累计占用、去重活跃墙钟、平均和最高并发。总阶段与子阶段可彼此嵌套，多个任务可同时等待。无心跳的短请求在该阶段报告零样本。

## 验证结果

- Go 1.26.11 隔离 overlay 下运行 `go test -count=1 -v ./internal/studio -run '^(TestQueryStageOverlap248|TestPostgresQueryStage.*248|TestPostgresOriginalQueryRateCurve040|TestQueryCurveBacklog040|TestPooledQuery|TestLargeQueryLimits040)'`，5 个顶层回归通过。区间重叠、零时长、截窗、分位数和采样溢出均有确定性断言。省略本机数据库配置，两个 248 PG 和一个 040 测量入口均按条件跳过。
- 同一 overlay 的 `go vet ./cmd/server ./internal/studio` 与 `go build ./cmd/...` 通过。
- 集成人使用本机隔离 PG，设置 `STUDIO_MEDIA_QUERY_TIMINGS=1`，串行运行 `go test -v -count=1 -timeout=5m ./internal/studio -run '^TestPostgresQueryStage.*248$'`。三档同时输出原 040 端到端口径和固定阶段汇总，另验首次与心跳都有样本。隔离开发期间未运行 PG。

## 风险与限制

040 显示三个档位的有效工作区和渠道预算均未触发范围拒绝。下一组可验证的实验是固定 128 个执行位及原到期序列，根据本次分阶段结果选择一个变量。若 `renew_pool_wait` 的持续占用和长尾明显，可对照 4 与 8 条查询连接，并核对是否把等待转移到选择或控制事务。若高占用集中在结果的应用锁等待和控制事务，先测能缩短该事务或应用锁持有时间的改动，保留租约、账务及事件的原子性。单写者同机短档、采样回调的开销和各阶段互相嵌套均应计入解释。6,000 次/秒及 24 小时稳态仍按原验收安排。

## 回滚方式

关闭测试入口可继续使用原 040 曲线。移除计时补丁可恢复原有执行代码，数据库及私有文件无需迁移。

## 集成人实库结果

两项明确开启的 PostgreSQL 用例共 34.400 秒通过。三档曲线 30.10 秒，慢 GET 心跳 4.15 秒。128 档完成 512 个唯一原 GET。在该档 3998.24 毫秒的测量窗口内，从执行入口至首次续租的 P95 为 233.79 毫秒，已知结果等待应用互斥的 P95/P99 为 271.76/289.72 毫秒。租约池等待 P95 为 4.61 毫秒，控制写事务 P95 为 5.93 毫秒，512 次保存事务的累计与去重墙钟均约 2347 毫秒。各阶段可并发或互相包含。此次独立测量中实际 200 毫秒上游服务峰值为 68；上次关闭计时的曲线单独保留。[各档分布](../wiki/assets/media-query-stage-timing-040.json)
